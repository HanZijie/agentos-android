## 结论（当前）

1. 监督契约按下文 a–f 执行。C 可以照着实现 `AgentService`、心跳和 `SupervisorStatusReceiver` 的接收端；D 在 W7 里把 `spikes/S2/device/supervisor.sh` 改成 `module/service.sh` 的监督循环。
2. **判活方式选定**：看进程是否存在（`pidof` + uid 校验），不看心跳是否过期。心跳只用来判断“死的时候有没有任务”。
3. **root 能做到的两件关键事，源码已确认**：root 可以启动不导出的 Service，也可以给不导出、带 signature 权限的接收器发广播。API 37 SDK 源码 `ActivityManager.checkComponentPermission()` 第一步就是 `canAccessUnexportedComponents(uid)`，对 `ROOT_UID` / `SYSTEM_UID` 直接返回 `PERMISSION_GRANTED`。
4. **还没有证据的**：root 用 `am start-foreground-service` 启动前台服务是否免于后台启动限制；`ActiveServices` 的源码本机和外网都没拿到，只能靠真机测。这是 S2 最关键的一条，不通过就走计划里的退路（电池优化豁免）。
5. 模拟已通过：状态机在电脑上用假 procfs 和虚拟时钟跑了 9 个场景、30 项断言，dash 和 bash-posix 下全部通过（见“已有证据”）。

## 监督契约 v0

下文的包名、类名都是正式 App 的名字。实验 App 的 `applicationId` 是 `org.agentos.spike.s2`，类名与正式 App 相同，权限名换成 `org.agentos.spike.s2.permission.*`，以免和正式 App 在同一台设备上冲突。

### a. AgentService：组件名与前台服务类型

| 项 | 值 |
|---|---|
| 组件 | `org.agentos.app/org.agentos.app.agent.AgentService`（`org.agentos.app/.agent.AgentService`） |
| 进程 | `android:process=":agent"`，进程名 `org.agentos.app:agent` |
| 导出 | `android:exported="false"`：只有 root 和本 App 能启动 |
| 前台服务类型 | `android:foregroundServiceType="specialUse"`，并声明 `<property android:name="android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE" android:value="…"/>` |
| 权限 | `FOREGROUND_SERVICE`、`FOREGROUND_SERVICE_SPECIAL_USE`、`POST_NOTIFICATIONS`（通知权限只影响通知是否可见，不影响前台服务本身） |
| 监督进程的启动命令 | `am start-foreground-service --user 0 -n org.agentos.app/.agent.AgentService -a org.agentos.action.SUPERVISOR_START --es org.agentos.extra.REASON <reason> --ei org.agentos.extra.ATTEMPT <n>` |
| `REASON` 取值 | `boot`（开机拉起一次，F2）、`restart`（有任务时死亡后退避拉起）、`promote`（有任务但没能进入前台，由 root 代为启动）、`safe_mode_exit`（退出 safe mode 后拉起一次）；W7 装完或升级 App 后用 `upgrade` |

`AgentService` 必须做到：

1. **每次 `onStartCommand` 先调用 `startForeground(id, notification, FOREGROUND_SERVICE_TYPE_SPECIAL_USE)`**，不管有没有任务，5 秒内完成（系统上限 10 秒）。原因：监督进程和 App 自己都用 `startForegroundService` 启动它，不调用 `startForeground` 就会被系统判为崩溃。
2. 然后执行恢复流程（每个进程只执行一次，F8）。恢复期间心跳写 `state=recovering`。
3. 恢复完成或任务全部结束后，如果没有任务：`stopForeground(STOP_FOREGROUND_REMOVE)` + `stopSelf()`，心跳写 `tasks=0 state=idle`。
4. 返回 `START_NOT_STICKY`：死后由谁拉起只由监督进程决定。K3 用例会实测 `START_STICKY` 下系统自己的重启行为，结果可能调整这一条。
5. 运行时在 `:agent` 里收到新任务、需要进入前台时，自己调用 `startForegroundService(本服务)`。如果抛出 `ForegroundServiceStartNotAllowedException`（后台、未豁免电池优化时预期会这样），**不要重试**，把心跳写成 `tasks>0 fg=0`。监督进程在 5 秒内用 `REASON=promote` 代为启动，服务照第 1 条进入前台（root 发起的 `startForegroundService` 把“允许进前台”记在这次启动上）。
6. `REASON=restart` 时，先读 `ActivityManager.getHistoricalProcessExitReasons()`：如果 `:agent` 上次的退出原因是 `REASON_USER_REQUESTED` 或 `REASON_USER_STOPPED`，就当作用户主动停止，不继续任务，写 `tasks=0` 后退出前台。这是为了覆盖“前台服务任务管理器里点停止”这类不会把包标为 stopped 的操作（用例 K5b 实测）。
7. `:agent` 进程的 `Application.onCreate` 保持轻量：状态广播接收器不在 `:agent` 里（见 e），但 bind 也会拉起 `:agent`。

### b. 心跳文件：路径、格式、写入频率

**路径**：`/data/user_de/0/org.agentos.app/files/supervisor/heartbeat`，即 `createDeviceProtectedStorageContext().filesDir` 下的 `supervisor/heartbeat`。

用设备加密（DE）存储，是为了让路径固定，并且在用户第一次解锁前后都能读写；心跳里没有敏感内容。

**格式 v1**：ASCII，每行 `key=value`，不超过 16 行、512 字节。

```text
v=1
pid=12345          # Process.myPid()
start=81234        # Process.getStartElapsedRealtime()，毫秒
at=95321           # 本次写入时的 SystemClock.elapsedRealtime()，毫秒（与 /proc/uptime 同一时钟，含休眠时间）
boot=17            # Settings.Global.BOOT_COUNT
tasks=1            # 未结束的任务数：排队中 + 执行中（含等待确认、等待工具）；“需要恢复、等用户处理”的不算
fg=1               # AgentService 当前是否处于前台
state=busy         # starting | recovering | idle | busy | stopping | crashed
```

- 监督进程只认整数字段和上面这组 `state` 枚举，其他内容一律忽略，不会执行文件里的任何东西；符号链接、FIFO 等非普通文件直接跳过。
- `state=starting` 或 `recovering` 时，`tasks` 不作数，监督进程沿用之前的判断。
- 写法：先写 `heartbeat.tmp`，再 `rename` 覆盖，保证监督进程读到的总是完整文件。
- 不许写进心跳：key、prompt、会话内容、错误详情。

**写入频率**：

| 时机 | 写什么 |
|---|---|
| 进程内第一次恢复开始时 | `state=recovering` |
| `tasks`、`fg`、`state` 任何一个变化时 | 立即写 |
| `tasks>0` 期间 | 每 30 秒写一次，刷新 `at`（只用于诊断） |
| 空闲（`tasks=0`） | 不写；进程可能被冻结或回收，这是正常的 |
| 未捕获异常 | 尽力写 `state=crashed`（保留 `tasks`），再交给系统默认处理 |

### c. 判活方式

- **活着** = 存在名为 `org.agentos.app:agent` 的进程，并且 `/proc/<pid>/status` 里的 `Uid` 等于 App 的 uid（取自 `stat -c %u /data/user_de/0/org.agentos.app`）。
  - 用 `pidof` 找进程。找到后每轮只检查 `/proc/<pid>` 是否存在，不再 fork。
  - 校验 uid，是因为其他 App 可以给自己的进程起同样的名字。uid 读 `status`，不用 `/proc/<pid>` 目录的属主：进程不可 dump 时，目录属主是 root。
- **不用心跳是否过期来判活**：屏幕关闭后 CPU 休眠，cached 进程还会被冻结，这时心跳会停写，但进程是好的。进程活着却卡死的检测不在 M1 范围，留给 W11。
- **心跳的用途**：判断进程死的时候有没有任务（下文称 need）。
  - need 取死掉的那个 pid 最后一次心跳里的 `tasks>0`，且 `state` 须为 `idle`、`busy`、`stopping` 或 `crashed`。
  - 如果心跳的 pid 不是死掉的那个（新进程还没来得及写就死了），沿用之前的 need。
  - 开机时，上一次开机留下的心跳如果 `tasks>0`，need=1。这样开机恢复期间反复崩溃也会被计数。
- **轮询间隔**：need=1 或正在等待重启时 1 秒；其他时候 5 秒。
- **用户强行停止**：进程死亡时，如果 `dumpsys package org.agentos.app` 的 `User 0:` 行里是 `stopped=true`，就不拉起，状态记为 `stopped / user_stopped`。

### d. 有任务时的退避与崩溃循环

| 参数 | 值 |
|---|---|
| 何时拉起 | 只在 need=1 的进程死亡后拉起；没有任务就不拉起，等下一个调用方 bind 时由系统拉起 |
| 退避延迟 | 第 n 次连续重启等待 min(2^(n−1), 60) 秒：1、2、4、8、16、32、60、60 … |
| 退避复位 | 运行时连续存活 60 秒后，下一次延迟回到 1 秒 |
| 崩溃循环 | 600 秒（`/proc/uptime`）内第 5 次死亡：不再拉起，写 safe mode 标记（`reason=crash_loop`）并广播 |
| 也算一次死亡 | 拉起命令报错；拉起后 15 秒内没看到进程 |
| 开机 | 等 `sys.boot_completed=1`，再等用户 0 解锁（`sys.user.0.ce_available=true`，每 30 秒兜底查一次 `am get-started-user-state 0` 是否为 `RUNNING_UNLOCKED`），然后用 `REASON=boot` 拉起一次 |
| 到点必拉 | 退避时间到了一律执行启动命令，即使期间已有 `:agent` 进程被 bind 拉起。这样 `AgentService` 的恢复流程一定会执行；对已在运行的进程，只是多一次 `onStartCommand` |

### e. 状态广播：action、extra、权限

**发送**（root，显式广播，**不带** `FLAG_INCLUDE_STOPPED_PACKAGES`，这样用户强行停止后不会被我们唤醒）：

```sh
am broadcast --user 0 -n org.agentos.app/.agent.supervisor.SupervisorStatusReceiver \
  -a org.agentos.action.SUPERVISOR_STATUS --ei org.agentos.extra.PROTOCOL 1 --es org.agentos.extra.STATE ok ...
```

**接收器声明**（W7 追加到 `app/src/main/AndroidManifest.xml`）：

```xml
<permission
    android:name="org.agentos.permission.SEND_SUPERVISOR_STATUS"
    android:protectionLevel="signature" />

<!-- 在主进程：状态广播不会拉起 :agent，也就不会干扰判活 -->
<receiver
    android:name=".agent.supervisor.SupervisorStatusReceiver"
    android:exported="false"
    android:permission="org.agentos.permission.SEND_SUPERVISOR_STATUS" />
```

`exported="false"` 加 signature 权限是双保险：root 两项检查都绕过（见结论 3），其他 App 两项都过不去。实验 App 里另有一个 `exported="true"`、只靠权限保护的变体，用例 P1 两种都测。如果真机上 root 送不进不导出的接收器，就改用导出版本，权限不变。

**Extras**：

| extra | 类型 | 含义 |
|---|---|---|
| `org.agentos.extra.PROTOCOL` | int | 契约版本，现在是 `1`；App 只处理自己认识的版本 |
| `org.agentos.extra.STATE` | String | `ok` \| `backoff` \| `safe_mode` \| `stopped` |
| `org.agentos.extra.REASON` | String | `ok`：`boot`、`runtime_up`、`safe_mode_exited`；`backoff`：`runtime_died`；`safe_mode`：`crash_loop`、`manual`，W11 / W12 增加 `unsupported_api`、`unsupported_fingerprint`、`migration_failed`；`stopped`：`user_stopped`、`module_disabled`、`supervisor_exited`、`not_installed` |
| `org.agentos.extra.SEQ` | long | 本次监督进程内递增，从 1 开始；App 按 (`BOOT_COUNT`, `SEQ`) 排序，丢弃旧的 |
| `org.agentos.extra.SINCE` | long | 进入当前状态的时间，epoch 毫秒 |
| `org.agentos.extra.DEATHS` | int | 600 秒窗口内的死亡次数 |
| `org.agentos.extra.BOOT_COUNT` | int | `Settings.Global.BOOT_COUNT` |
| `org.agentos.extra.MODULE_VERSION` | String | `module.prop` 的 `version` |
| `org.agentos.extra.MODULE_VERSION_CODE` | int | `module.prop` 的 `versionCode` |
| `org.agentos.extra.RUNTIME_PID` | int | 当前观察到的 `:agent` pid，`0` 表示未运行 |

**发送时机**：状态变化时；每发现一个新的 `:agent` 进程时。所以运行时每次启动后 5 秒内一定会收到一条。

**App 这边要做的**：

- 接收器只校验 `PROTOCOL`，把字段写进 DE 存储的 `supervisor/status`，`:agent` 和界面都从那里读，经 `IAgentControl` 展示。
- “监督进程未运行”的判定：运行时启动 30 秒后，还没有收到 `BOOT_COUNT` 与当前一致的状态广播。
- `stopped / user_stopped` 这条广播通常送不到（App 此时处于 stopped 状态），这是预期的；`module.prop` 的描述里仍会显示。

### f. safe mode 标记

| 项 | 值 |
|---|---|
| 标记文件 | `/data/adb/agentos/safe_mode`：存在即 safe mode |
| 内容 | `reason=<[a-z0-9_]+>`、`since=<epoch 秒>`、`deaths=<uptime 列表>`，每行一个 `key=value` |
| 谁来写 | 监督进程（崩溃循环；W12 起还有 OTA 后版本超出范围、迁移失败）；W11 的 `action.sh`（手动进入） |
| 谁来删 | W11 的 `action.sh`（手动退出）。删除后监督进程报告 `ok / safe_mode_exited`，并用 `REASON=safe_mode_exit` 拉起一次 |
| safe mode 下 | 不拉起运行时，但继续追踪进程；运行时被 bind 拉起时照样收到 `safe_mode` 广播，据此不自动继续恢复出来的任务 |
| 同一目录下的其他监督状态 | `supervisor.log`（超过 256 KiB 轮转一次）、`status`、`supervisor.pid`。该目录只有 root 可读（0700），模块升级不覆盖，卸载时由 `uninstall.sh` 整个删除（F13） |
| App 怎么知道 | App 读不了 `/data/adb/`，只能靠 e 的广播；root 管理器里的模块描述同步显示 `[安全模式] 原因：…` |

监督进程收到 TERM（例如关机）时，如果正处于 safe mode，保留 safe mode 的描述，不改成“已停止”。

## 为什么这样选

| 决定 | 理由 | 放弃的做法 |
|---|---|---|
| 判活看进程，不看心跳是否过期 | 屏幕关闭后 CPU 休眠，cached 进程还会被冻结，心跳停写不代表进程死了；按心跳过期去杀或重启，会误伤正常进程 | 心跳超时即重启 |
| 心跳放在 DE 存储 | 路径固定，第一次解锁前后都能写；root 读取不受 CE 加密影响 | CE 的 `files/`（解锁前不可用） |
| root 只读心跳里的整数和固定枚举 | 原则 2：root 进程不解析不可信输入。心跳由 App 的 uid 写，按最小信任解析 | `source` 或 `eval` 心跳文件 |
| 状态接收器放在主进程 | 广播会拉起接收器所在进程。放在 `:agent` 会让一条状态广播凭空拉起运行时，干扰判活 | 放在 `:agent` |
| 有任务但进不了前台时由 root 代为启动 | 后台 App 调用 `startForegroundService` 在 Android 12 及以上会被拦；root 发起的启动不受这个限制（待 T1 验证） | 只依赖电池优化豁免 |
| `START_NOT_STICKY` | 避免系统和监督进程同时拉起、各自计数；系统重启 sticky 服务时能否再进前台也没有保证 | `START_STICKY`（K3 实测后再定） |
| 等用户解锁后再拉起 | App 不是 directBootAware，解锁前系统不会启动它的组件 | 只等 `sys.boot_completed` |

## 测试用例

每个用例都要在 API 35、36、37 和 Magisk、KernelSU 的组合上各跑一遍。驱动脚本是 `spikes/S2/s2.sh`，设备端辅助脚本是 `s2dev.sh`。

| # | 做法 | 通过标准 | 对应计划中的 S2 条目 | 结果 |
|---|---|---|---|---|
| B0 | 装模块后重启，解锁 | root 用 `am start-foreground-service` 启动成功（没有 `Error`），`dumpsys activity services` 显示前台；记录从解锁到进程起来的耗时 | root 拉起前台服务不被后台启动限制拦截 | 待测 |

| K2 | 连续杀 5 次 | 退避为 1、2、4、8 秒；第 5 次后不再拉起，进入 `safe_mode / crash_loop`，App 收到广播；删除标记后恢复 | 崩溃循环参数 | 待测 |
| K3 | 用 `S2_STICKY=true` 构建，重复 K1 | 记录系统自己的重启时间，以及重启后能否 `startForeground`，据此定 sticky 策略 | — | 待测 |
| K4 | 有任务时让 `:agent` 抛出未捕获异常 | 心跳为 `state=crashed`，按退避拉起 | — | 待测 |
| K5 | 有任务时 `am force-stop` | 90 秒内不拉起，状态为 `stopped / user_stopped` | — | 待测 |
| K5b | 有任务时在前台服务任务管理器里点“停止” | 记录包是否被标为 stopped、`ApplicationExitInfo` 的原因；验证 a 第 6 条 | — | 待测 |
| B1 | 灭屏，`dumpsys deviceidle force-idle`，拔电（`dumpsys battery unplug`）30 分钟，然后让另一个 App bind | 从 bind 到首个响应不超过 3 秒（实验 App 冷启动很轻，正式运行时还要加上加载 `pi-agent.js` 的时间） | 灭屏 30 分钟后 bind 到首个响应 ≤ 3 秒 | 待测 |
| T1 | 未豁免电池优化，灭屏，由后台 App bind 并发起任务 | 记录 `:agent` 自己调用 `startForegroundService` 的结果；如果被拒，监督进程在 5 秒内 `promote`，心跳变成 `fg=1` | 退路：电池优化豁免 | 待测 |
| L1 | 一个长任务占 150 MB，拔电连续运行 24 小时，每 5 分钟记一行 | `pid_changes=0`；记录 PSS 的最大值和平均值，以及 `exit-info` | 24 小时不因 Android 17 的内存上限被回收，并记下内存占用 | 待测 |
| P1 | 另一个 App（不同证书）和 `adb shell`（shell uid）分别向两个接收器发同样的广播，再用 root 发 | 前两者都送不进（logcat 有 `Permission Denial`），root 两个都送得进 | App 能收到监督进程的广播，其他 App 发不进来 | 待测 |

| 构建 | `sh spikes/S2/build.sh`（AGP 8.10.1、Kotlin 2.2.20、JDK 21、compileSdk/targetSdk 36、minSdk 35） | 两个 APK 和模块 zip 构建成功 |

模拟时发现并修掉了两个问题：

1. 关机时收到 TERM，会把 safe mode 的描述改写成“已停止”；
2. 中文字符串里紧跟 `$VAR` 的中文字节，会被 bash 3.2 当成变量名的一部分，导致变量展开为空。现在中文字符串里的变量一律写成 `${VAR}`。设备上的 mksh 和 busybox ash 会不会中招未测，统一加大括号后都不受影响。

### 整合时在模拟器上的观察（2026-09-29，不需要 root 的部分）

设备：AVD `Pixel_8a`（API 36，Google Play 镜像，user 构建，**没有 root**），所以 B0–L1 等依赖 `su` 的用例都没有跑。App 自己在前台操作：

| 内容 | 结果 |
|---|---|
| App 在前台时用 `startForegroundService` 开任务 | 系统放行（`Background started FGS: Allowed … uidState: TOP`），拉起 `:agent` 进程 |
| 热进程（恢复已完成）里开任务 | ✅ `isForeground=true`，`types=0x40000000`（specialUse）；心跳写在 DE 存储，`tasks=2 fg=1 state=busy` |
| 停止全部任务 | ✅ 退出前台、服务销毁，心跳 `tasks=0 fg=0 state=idle` |
| P1 不需要 root 的一半：另一张证书的 App 和 shell 身份冒充监督广播，发给两种接收器 | ✅ 都没有送达（没有 `STATUS_RECEIVED` / `STATUS_IGNORED`）；启动不导出的 `AgentService` 被拒（`SecurityException`） |
| **冷进程里开任务** | ❌ **缺陷**，见下 |

**缺陷（W6 实现 `AgentService` 时要避开）**：进程刚起、恢复流程还没跑时，`START_TASK` 的顺序是 `startForeground` 成功 → `Runtime.add()` 先调 `ensureLoaded()`，恢复结束时 `onChanged()` 看到任务数为 0，调用 `onIdle()` 退出前台并 `stopSelf()` → 之后才登记任务 → `SERVICE_DESTROY`。结果任务在跑，服务却已不在前台（心跳 `tasks=1 fg=0`）。有 root 监督时会被 `REASON=promote` 掩盖，没有监督时任务失去前台保护。规则：**恢复流程结束时的“空闲判断”必须在本次命令携带的任务登记之后再做**（或者恢复阶段不触发 `onIdle`）。

**给 W8**：`targetSdk` 36 强制 edge-to-edge，实验 App 最上面两个按钮被标题栏盖住，点不到（这里改用键盘焦点操作）。正式界面要处理 window insets。

## 待确认与风险

1. **root 发起的前台服务启动是否受后台限制**（B0、T1）：框架层的组件权限检查已确认会放行 root；`ActiveServices` 里后台启动 FGS 的豁免逻辑没有核对到源码。
2. **`sys.user.0.ce_available`**：按 vold 的行为推断解锁后会被置为 `true`，未核对源码；脚本每 30 秒兜底查一次 `am get-started-user-state`，日志会记下是哪条条件生效的。
3. **`pidof` 在 busybox 独立模式和 toybox 下对长进程名的匹配**：Android 的 `comm` 会截断成 `app:agent`，两者都应该退回去比对 `argv[0]`，待真机确认。
4. **前台服务任务管理器的“停止”**不一定把包标为 stopped（K5b），所以 a 第 6 条要求运行时自己查 `ApplicationExitInfo`。
5. **监督进程自身会不会被回收**：它的 `oom_score_adj` 继承自 root 管理器，`s2dev.sh info` 会记录下来；目前没有主动调整。
6. **Android 17 的内存上限**：L1 在 API 37 上的结果决定需不需要走 standby bucket 或 deviceidle 白名单的退路。
7. **USB 连接会让设备一直处于充电状态，不进入 Doze**：B1、T1、L1 必须 `dumpsys battery unplug` 或者拔线测试。
