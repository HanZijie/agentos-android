两条退路（后台 bind 不可靠时只在有任务时 bind；读不到 assets 时经 Binder 返回插件包）都用不上。

## 方法

- **两个进程的分工**：`:agent` 用 `BIND_AUTO_CREATE` 绑定 `:ext`（`ExtensionClient`）。`:ext` 里跑的是 A 的纯 JVM 部分（`PluginScanLogic`、`ApprovalStore`、`ExtensionToolHost`、`ExtensionSkillPort`），加上 C 的 Android 适配（`AppPluginScanner`、`BinderMcpConnector`、`AssetSkillFileSource`）。
- **驱动方式**：回归脚本通过 debug 包里的 `ExtensionDebugReceiver` 驱动 `:ext`（主进程 → IExtensionHost，与插件管理页走同一条路径）。端到端用例由 in-app 执行器让真实运行时调用插件工具，模型是本机上的假模型端点。
- **前置条件**：测试前先从**前台界面**打开电脑端接入（in-app 的 `desktop-access` 场景），让 `:agent` 保持前台服务并持有对 `:ext` 的绑定。这和“有任务时”的前台理由相同（C6）。

## 发现

1. **`:ext` 和插件进程的优先级跟着 `:agent` 走。**
   - `:agent` 在前台服务时，`:ext`（BIND_AUTO_CREATE）和它 bind 的插件进程都是 procState 4，不会被冻结。
   - `:agent` 没有前台理由时，三者都是 cached（19），会被 cached-apps freezer 冻结。这时调用仍然能成功（每次 bind / 广播会临时提高优先级），但 `ExtensionToolHost` 的空闲计时器要等解冻后才走。
   - 运行时只在有任务（前台服务）时调用工具，所以不影响实际行为。但设备用例必须从前台界面打开电脑端接入：在后台收到的广播里，`:agent` 启动不了前台服务（Android 12+ 的后台启动限制，C6 已知，由监督进程 promote）。
2. **同一进程的广播是串行投递的。** 调试入口的 `call` 用 goAsync 占住广播，直到调用结束；这期间再发的广播（例如停用插件）要等它结束才送到。所以“调用中停用”这类用例改为在 `call` 里定时执行（`disableAfterMs`）。只影响测试驱动。
3. **签名轮换也算签名变化。**
   - v3 lineage 轮换后，`SigningInfo.apkContentsSigners` 返回新证书，摘要随之变化，状态变为 `signature_changed`，需要用户确认。
   - 这符合 A8 的保守规则，代价是合法的密钥轮换也会让用户确认一次。
   - 如果要放行“经 lineage 证明的轮换”，适配层可以把 `signingCertificateHistory` 一起交给 `PluginScanLogic`（已在 C7b 报告里向 A 提出）。
4. **卸载会清掉记忆。** 所以“卸载后换签名重装”会被当作新插件（默认关闭），而不是签名变化。用户策略也随卸载清掉，没有安全问题。
5. **不需要额外权限。** `queryIntentServices`、`getPackageInfo(GET_SERVICES | GET_META_DATA | GET_SIGNING_CERTIFICATES)`、`createPackageContext(包名, 0).assets` 在 API 35–37 上都不需要额外权限。插件包对 AgentOS 可见，靠的是 Manifest 里 `<queries>` 的 PLUGIN action。
6. **负载高时暴露过一个竞态（已修）。** `:ext` 为了让插件页列出被禁用的工具，会记住见过的工具。最初的清理规则是“不在目录、按策略又是启用的就删”，而目录和策略是两个流：
   主机负载很高时（load average 20–29），combine 先看到去掉 echo 的新目录、后看到新策略，echo 被误删，之后既列不出来也启用不回去。
   现在记录只在插件不再可用时删，列不列出改在 listTools 时按当前策略计算。
