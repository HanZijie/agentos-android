## 要回答的问题

在 `service.sh` 里用 `pm install` 安装和升级 zip 里的 APK，Magisk 和 KernelSU 下是否都可行：开机后能装、能覆盖升级、不被 Play Protect 拦截；签名不符时正确停止，并在 root 管理器里显示原因。不行的话退到在 `customize.sh` 刷入阶段安装，再不行就让用户手动安装。

## 结论（当前）

1. 安装规则已定，W7 直接沿用 `spikes/S1/module/s1lib.sh` 的逻辑，见下一节。
2. **安装方式定为：先复制到 `/data/local/tmp` 再装，失败再用管道。** 在 API 35 / 37 模拟器（adb root，`u:r:su:s0`，SELinux Enforcing）上：
   - 直接给 `pm` 模块里的路径不行：`system_server` 读不了 `/data/adb`（`adb_data_file`），日志里是 `avc: denied { read } … tcontext=u:object_r:adb_data_file:s0`；
   - 把模块里的文件重定向给 `pm` 的 stdin 也不行（`Failed transaction`），session 方式同样失败；
   - 复制到 `/data/local/tmp`（`shell_data_file`，system_server 可读）成功，160–690 ms；`cat apk | pm install -S` 的管道也成功，约 530 ms。
   - Magisk 的 `u:r:magisk:s0` 和 KernelSU 下规则可能更宽，但 `/data/adb` 的标签一样，按最保守的顺序走。
3. 版本比较、不降级、签名不符停止（保留已装版本和数据）、刷入阶段安装的退路，在 API 37 模拟器上都通过。
4. **测试用例设计的修正**：换签名的测试包必须比已装版本新，否则按版本规则会被“同版本跳过”，根本走不到安装。M5 改用 v3（key b）装在 v2（key a）上。这也说明：versionCode 相同、证书不同的情况模块发现不了（不装，也不报错），见“待确认与风险”第 6 条。
5. Play Protect：google_apis 镜像没有 Play 服务，模拟器上无法观察，M8 仍待真机。

## 安装规则（W7 照此实现）

1. **清单**：zip 里的 `app/apks.list` 每行一个 APK，格式为 `<包名> <versionCode> <zip 内路径> <SHA-256> <签名证书 SHA-256>`，由 `tools/package-module.py` 生成（W7 加了第 5 个字段，给 `tools/check-device.sh` 比对手机上已装版本的证书用）。模块在设备上不需要 `aapt`，也不用自己解析 APK。W7 的实现在 `module/apks.sh`，由 `module/service.sh` 调用。
2. **时机**：`service.sh` 先等 `sys.boot_completed=1`，再等 `pm path android` 能返回（最多约 2 分钟），然后安装。安装不必等用户解锁；拉起运行时要等解锁（S2 契约 d）。
3. **完整性**：安装前核对 SHA-256，不符就停止，并显示原因。
4. **版本比较**（`pm list packages --show-versioncode <包名>`）：

   | 手机上 | 动作 |
   |---|---|
   | 没装 | `pm install -r` |
   | versionCode 更低 | `pm install -r`（覆盖升级，保留数据） |
   | 相同 | 跳过 |
   | 更高 | 跳过，**不降级**（不加 `-d`） |

5. **安装方式**：按“复制到 `/data/local/tmp` → 管道（`cat apk | pm install -S <size>`）→ 路径 → stdin 重定向（`-S <size>`）→ session（`install-create` / `install-write` / `install-commit`）”依次尝试（模拟器结果见 M7）。只有 I/O 类失败才换下一种方式；以下语义类失败直接停止：`INSTALL_FAILED_UPDATE_INCOMPATIBLE`、`VERSION_DOWNGRADE`、`VERIFICATION_FAILURE`、`INSUFFICIENT_STORAGE`、`USER_RESTRICTED`、`DUPLICATE_PERMISSION`、`ABORTED`、`INSTALL_PARSE_FAILED_NO_CERTIFICATES`。真机结果出来后，只保留实际需要的几种方式。
6. **签名不符**（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`）：停止；**绝不自动卸载旧版**，卸载会清掉用户数据。把原因写进 `module.prop` 的 `description`（Magisk 和 KernelSU 的模块列表都显示这个字段），同时写日志。之后每次开机会再试一次，代价很小。
7. **`pm` 的标准输入**：`pm` 实际是 `cmd package`，会把自己的 stdin 交给 system_server。在 `while read … < 清单` 这样的循环里，所有不需要传 APK 内容的 `pm` 调用都要加 `</dev/null`，否则会吞掉清单剩下的行。`lib-test.sh` 有专门的用例，变异测试确认它能抓到这个问题。
8. **记录**：从开机完成到 `pm` 就绪的耗时、每次安装的方式和耗时、`package_verifier_enable` 和 `verifier_verify_adb_installs` 的值（只读，不修改），供分析 Play Protect 的行为。
9. **装完之后**：安装或升级了 AgentOS App，就按 S2 契约用 `REASON=upgrade` 拉起一次运行时；但包处于 stopped 状态时不拉起（全新安装的包都是 stopped，见 S2 v0.1 修正 #4）。

**退路：刷入阶段安装**。从已开机的 root 管理器 App 里刷入时（`BOOTMODE=true`），`customize.sh` 直接执行同一套逻辑；从 recovery 刷入则推迟到 `service.sh`。对应测试包 `s1-v3-customize.zip`。

## 待确认与风险

1. **路径方式**：模拟器上 adb root（`u:r:su:s0`）不行，system_server 读不了 `adb_data_file`。Magisk（`u:r:magisk:s0`）和 KernelSU 下，文件标签相同，预计同样不行；默认顺序已经不依赖它。
2. **Play Protect**：root 安装在系统看来接近 adb 安装。“通过 USB 验证应用”开启时可能触发扫描，安装会因此变慢或出现提示；M8 要在带 Play 服务的真机上记录。
3. **Android 开发者验证**：Google 在 developer.android.com 上有 Android developer verification 的页面，但它对 root / adb 安装的适用范围我没能查证（页面正文没取到），列为 M8 的观察项。如果 root 安装也受限，影响的是整个交付形态，需要整合人决定对策。
4. **用户解锁前安装**：日志会记下安装时的 `sys.user.0.ce_available`。模拟器开机即解锁，没测到解锁前的情况。
5. **安装拖慢开机**：`service.sh` 在后台运行，不阻塞开机；模拟器上单个 APK 160–690 ms。
6. **versionCode 相同、证书不同**：模块按“已是同版本”跳过，不会发现证书不同。这种情况只会出现在用户自己装了另一个签名的同名包时；W7 的 `check-device.sh` 用 `dumpsys package` 核对证书并提示，`service.sh` 不处理。
7. **`/data/local/tmp` 里的临时副本**：安装期间短暂存在（`agentos-install-<pid>.apk`，0644），装完即删。shell uid 在这段时间可以读到 APK，但 APK 本身是公开发布物，不含秘密。
