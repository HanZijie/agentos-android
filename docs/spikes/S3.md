## 结论

**可以用，按计划推进。** 官方 SDK 0.30.1 的 Client 和 Agent 端经 `BinderAcpTransport` 在 Android 15 / 16 / 17（模拟器）上跑通了 `initialize` → `session/new` → 流式 `session/prompt` → `session/cancel` → close / 重新 bind；两端进程被杀、超长消息、违规注入、电脑端经 `adb forward` 用官方 TypeScript 客户端对话也都通过。R8 release 与 debug 行为一致；R8 只需要一条 `-dontwarn org.slf4j.**`（与下面第 2 条同源），不需要 keep 规则。

但 W5 必须带上下面几处处理，否则在设备上会出问题（详见“发现的问题”）：

1. **`IChannel` 要加一个 `ack` 方法做流控。** oneway 调用没有回执，不加流控时发送方几毫秒内就能写满接收方约 508 KiB 的 Binder 异步缓冲（8 KiB 的消息 0.3 ms，1 KiB 的消息 4 ms），之后连 `close` 都发不过去，对端会永远挂住。
2. **SDK 在 Android 上第一次记日志就崩溃**（kotlin-logging 默认走 slf4j，而 slf4j 不在 APK 里），R8 也会因此报 Missing class。要在任何 SDK 类记日志之前设置系统属性 `kotlin-logging-to-android-native=true`，并在库的 consumer 规则里加 `-dontwarn org.slf4j.**`。
3. **SDK 按接口类型编码 JSON-RPC 时，每条消息多一个 `"type"` 字段**，SDK 自带的 `StdioTransport` 就是这样输出的。Binder 通道按具体类型编码，电脑端网关也不要直接用 `StdioTransport`。
4. **SDK 的 `Protocol` 不会在 Transport 关闭时结束挂起的请求。** 接线时要在 Transport 的 `onClose` 里调 `protocol.close()`，否则对端死亡后本端的 `prompt` 会永远等下去。

## 已确认的事实

- Android 15 对应 API 35，Android 16 对应 API 36，Android 17 对应 API 37。[Android API level 表](https://developer.android.com/guide/topics/manifest/uses-sdk-element)
- SDK 的 JVM 目标是 **Java 8 bytecode**，构建工具链要求 JDK 21。源码没有声明 `androidTarget()`，只有 JVM、JS、Wasm、iOS 等 target。[构建配置 v0.30.0](https://github.com/agentclientprotocol/kotlin-sdk/blob/v0.30.0/buildSrc/src/main/kotlin/acp.multiplatform.gradle.kts)
- Gradle 会把 `com.agentclientprotocol:acp:0.30.1` 自动解析到 JVM 变体 `acp-jvm`。[Maven Central 目录](https://repo1.maven.org/maven2/com/agentclientprotocol/acp/0.30.1/)
- Android 的 D8 / R8 支持 Java 8 bytecode 和相关 desugaring，因此这个结果符合 Android 的运行方式。[Java 8 支持说明](https://developer.android.com/studio/write/java8-support)
- Maven Central 上 0.30.1 正式包里的版本常量是 `0.30.1-dev-67`，不能用它判断版本；主工程的 `AcpSdkVersionLockTest` 检查的是加载的 jar 名（`acp-jvm-0.30.1.jar`）和 Transport 签名。
- GitHub 上没有 `v0.30.1` 的 tag（有 v0.30.0、v0.31.0、v0.32.0）。第二部分引用的 0.30.1 源码取自 Maven Central 的 [acp-jvm-0.30.1-sources.jar](https://repo1.maven.org/maven2/com/agentclientprotocol/acp-jvm/0.30.1/acp-jvm-0.30.1-sources.jar)。

### 结果：Binder 本身的边界

不经过 `BinderChannel`，直接对一个 oneway 接口连发（`IBenchSink`），三个 API 版本、debug 与 release 的结果完全相同：

- **单条上限**：接收方空闲时，单个 oneway 事务的 Parcel 最多约 520,192 字节，正好是接收方异步缓冲的大小（(1 MiB − 8 KiB) / 2）。换算成载荷：`String` 259,072 字符（中文、英文一样，都是 UTF-16），`byte[]` 519,168 字节。超过时抛 `TransactionTooLargeException: data parcel size 524384 bytes`。
- **慢接收方**（每条处理 2 ms）：发送方连发，在途约 390–510 KB 时失败，即整个异步缓冲写满。1 KiB 的消息第 242 条失败，用时 3.9 ms；64 KiB 的消息第 3 条就失败。两个方向（客户端 → `:agent`、`:agent` → 客户端）一样。
- **接收方不慢也会被写爆**：接收方不做任何处理，1 KiB 的消息在第 242–3,361 条之间失败，8 KiB 在第 33–95 条失败（各次运行不同）。只有 64 字符的小消息连发 2 万条没有失败（release 11–17 万条/秒）。
- **失败的表现**：Java 层抛 `DeadObjectException: Transaction failed on small parcel; remote process probably died, but this could also be caused by running out of binder buffer space`，内核错误是 `-28 (No space left on device)`，**但对端仍然活着**（`isBinderAlive` 为 true）。系统日志同时出现 `IPCThreadState: Process seems to be sending too many oneway calls`（oneway spam 检测，只记日志，没有杀进程）。

### 结果：流式延迟与吞吐

延迟是端到端的：从假 Agent 发出一条 `agent_message_chunk`（记 `elapsedRealtimeNanos`，同一台设备上跨进程可比）到客户端从 SDK 的 `prompt` Flow 里拿到它。

**固定速率**（每条 16 字符，带生产者背压，API 36，release；每档 4 秒）：

| 速率（目标） | 实际 | p50 | 最后 10% 的均值 | p99 |
|---|---|---|---|---|
| 100 条/秒 | 85 条/秒 | 0.90 ms | 1.0 ms | 3.7 ms |
| 200 条/秒 | 166 条/秒 | 0.98 ms | 1.1 ms | 7.9 ms |
| 500 条/秒 | 418 条/秒 | 0.87 ms | 0.9 ms | 8.3 ms |
| 1,000 条/秒 | 823 条/秒 | 1.00 ms | 1.2 ms | 7.9 ms |
| 2,000 条/秒 | 1,718 条/秒 | 0.99 ms | 1.0 ms | 19.5 ms |
| 4,000 条/秒 | 3,384 条/秒 | 1.05 ms | 1.1 ms | 37.8 ms |

实际速率低于目标，是假 Agent 用 10 ms 的 `delay` 分批发送的误差。

在这些速率下都**没有延迟堆积**：稳态延迟在 1 ms 左右，p99 的尖峰出现在每个场景开头（客户端进程刚启动，JIT 和类加载），之后回落。三个 API 版本上 100 条/秒的 p50 在 release 下都是 0.7–1.0 ms，debug 下 1.0–4.0 ms。Pi 的流式输出预计在每秒几十到几百条。

**打满**（每条 64 字符，不限速，带生产者背压，2 万条，API 36，release，每组跑两次）：

| 窗口（条 / 字符） | 吞吐 | p50 | p99 |
|---|---|---|---|
| 8 / 16,384 | 12,276、13,421 条/秒 | 3.4、3.0 ms | 36、43 ms |
| 16 / 32,768 | 17,103、16,002 条/秒 | 2.5、2.5 ms | 55、84 ms |
| **32 / 32,768（默认）** | **19,824、19,496 条/秒** | **2.9、2.7 ms** | **85、144 ms** |
| 64 / 65,536 | 20,299、18,375 条/秒 | 4.6、120 ms | 188、305 ms |

每条 16,000 字符的大块流式：32 / 32,768 约 1,200 条/秒，64 / 65,536 约 1,400 条/秒，p50 都在 5 ms 左右。

窗口越小，吞吐越低；窗口越大，开头的瞬态积压越大（64 条那组第二次 p50 到了 120 ms）。32 条 / 32,768 字符的吞吐与 64 条相当，在途字节只有一半，定为默认值。不带生产者背压时，打满会在 `:agent` 的发送队列里积压（最多约 96 万字符），延迟随之涨到数百毫秒到 1 秒以上，这是生产快于消费的正常排队，不是通道的问题；所以要求流式输出的生产者用 `awaitWritable` 做背压。

**主线程**：所有版本、所有场景里，两端在主线程上发生的 Binder 调用都是 0；客户端主线程上只有每 250 ms 一次的界面刷新。客户端主线程每 10 ms 一次心跳：release 下最大延后 22–52 ms，超过 50 ms 的只有 1 次（共约 4,000 次心跳）；debug 下 API 35 / 37 最大到 113 / 131 ms，超过 50 ms 的分别为 6 / 15 次（各约 4,500 次）。这些延后出现在 debuggable 进程上，推测是模拟器上的 GC、JIT 和调度，要在真机上复核。

### 结果：取消、断开与进程死亡

- **cancel**：100 条/秒时，从调用 `cancel` 到这一轮以 `CANCELLED` 结束 1–5 ms（release）、3–17 ms（debug），同一会话随后的 prompt 正常以 `END_TURN` 结束。打满时 cancel 要等已经排队的更新先送完（SDK 在返回 `PromptResponse` 之前会把本轮的更新排空）：带生产者背压 36–370 ms，不带时 0.19–2.5 s。
- **杀 `:agent`**（SIGKILL，流式中途）：客户端经 `linkToDeath` 在 5–47 ms 内感知，挂起的 `prompt` 在 6–74 ms 内以 `CancellationException("Protocol closed")` 结束，没有挂住；系统 1.04–1.28 s 后重建服务，重新 open 后对话正常。客户端没有残留通道。
- **杀客户端**（流式中途自杀）：`:agent` 在 6–26 ms 内以 `peer_died` 关闭通道，进行中的 prompt 被取消，连接、通道、协程、在跑的 prompt 都归零。
- **重新 bind**：bind → 握手 → 对话 → close → unbind 连续 20 次都成功，release 下每次 5–118 ms，debug 下 15–282 ms（每轮第一次更慢，28–447 ms）；结束后两端的连接数、通道数、协程数、在跑的 prompt 都是 0。不调 close、直接 unbind 并取消作用域，`BinderChannel` 也会通知对端关闭，同样没有残留。
- **超长消息**：客户端发超过 65,536 字符的 prompt，`BinderAcpTransport` 不发出，本地合成错误响应，`prompt` 在 3–60 ms 内以 `JsonRpcException` 失败，连接不受影响；65,536 − 1,024 字符的 prompt 正常；Agent 端要发超长的通知时丢弃该条，本轮其他更新照常，以 `END_TURN` 结束；绕过 SDK 直接往 `:agent` 的接收端塞 65,537 字符，`:agent` 判违规并关闭通道，客户端收到原因。
- **绕过流控塞消息**：连发 30,000 字符的消息，`:agent` 在未 ack 达到 2 条、60,000 字符时以 `window exceeded` 关闭通道（客户端在收到关闭前共塞进 2–9 条）。

### 结果：电脑端

`adb forward tcp:8765 localabstract:agentos-acp` 之后，官方 TypeScript SDK 1.5.1 的 `ClientSideConnection` 完成 `initialize` → `session/new` → prompt（`end_turn`）→ 长 prompt 中途 `cancel`（`cancelled`，3–12 ms）→ 再次 prompt（`end_turn`），三个版本的 debug 和 release 包都通过。API 36 是 user 构建，release 包不可调试，adbd 连接 App 的抽象 socket 也没有被拦。服务端回的每条消息都带 `"type"` 字段（问题 3），TypeScript 客户端忽略了它。一次性配对码属于 W9，这里没有做。

### 定下来的参数

写进 `core/protocol/binder-channel-v1.md` 第 8 节：

| 参数 | 值 |
|---|---|
| 单条上限 | 65,536 字符（`String.length`，约 128 KiB），占接收方异步缓冲的 1/4 |
| 在途上限 | 32 条，且 32,768 字符（约 64 KiB）；在途为 0 时单条不超过上限的消息总能发出 |
| ack | 每处理 8 条、8,192 字符，或处理完已收到的全部消息时回一次累计值 |
| 发送方本地积压上限 | 4,194,304 字符，超过就关闭通道 |
| ack 超时 | 窗口满后 30 s 收不到 ack 就关闭通道 |
| 生产者背压 | 流式输出每条之前等本地积压降到 16,384 字符以下 |
| close / ack 失败重试 | 10、50、200、1,000、3,000 ms |

初定的“128 KiB”按字节理解可以保留：Java AIDL 的 `String` 是 UTF-16，65,536 字符在 Parcel 里就是 128 KiB。若要让纯英文 JSON 能到 128 KiB，只能把 `String` 换成 UTF-8 的 `byte[]`（单条上限翻倍、要多一次编解码）；ACP 的消息大多很小，大内容走 `resource_link`，所以保留 `String`。

### 发现的问题与处理

1. **不加流控会写爆接收方的 Binder 缓冲，连 close 都发不过去。** 在 API 36 上关掉流控跑“打满”8 次，5 次在 `:agent` → 客户端方向写满了客户端的异步缓冲（内核 `-28 ENOSPC`）；最终矩阵里六组中也有两组写爆。加重试之前，`:agent` 随后发出的 `close` 也因为同样的原因失败，客户端永远收不到关闭，`prompt` 一直挂住直到场景超时（debug、release 各一次）。开流控的所有运行里没有出现过一次。处理：`IChannel` 加 `ack`，按窗口限制在途；`close` 和 `ack` 发送失败而对端仍活着时按退避重试，此后负向实验都在有限时间内以带原因的关闭结束。
2. **SDK 第一次记日志就崩溃。** SDK 0.30.1 依赖 kotlin-logging 7.0.0，Gradle 在 Android 上解析到它的 Android 变体；这个变体没有设置系统属性 `kotlin-logging-to-android-native` 时走 slf4j，而 slf4j-api 只是它的 compileOnly 依赖，不在 APK 里。结果是第一次 `prompt` 就抛 `NoClassDefFoundError: org/slf4j/LoggerFactory`（`ClientSessionImpl` 的静态初始化）。编译和 D8 发现不了；R8 在真正引用 SDK 时会报 `Missing class org.slf4j.*` 并失败。处理：`AcpAndroid.ensureInitialized()` 设置该属性，改用 `android.util.Log`；`BinderAcpTransport` 的静态初始化和 `:agent` 的入口都先调用它；`acp-android` 的 consumer 规则加 `-dontwarn org.slf4j.**`，App 自己不用加任何规则（已验证）。另一种做法是加 `org.slf4j:slf4j-api` 运行时依赖（日志被丢弃），需要改版本锁定表，没有采用。JVM 上（电脑上的测试）同理：kotlin-logging 的 JVM 变体看的是 `kotlin-logging-to-jul`，不设置又没有 slf4j-api 时同样会崩。
3. **SDK 编码的 JSON-RPC 多一个 `"type"` 字段。** `JsonRpcMessage` 是 `@Serializable sealed interface`，`ACPJson` 没有关掉类鉴别字段，按接口类型编码（`StdioTransport` 就是这么做的）会输出 `{"type":"com.agentclientprotocol.rpc.JsonRpcRequest","id":7,...}`。Kotlin 对端和 TypeScript 1.5.1 都忽略它，但它不是干净的 JSON-RPC。处理：`JsonRpcCodec` 按具体类型编码（有单元测试）；电脑端网关（W9）应基于 `JsonRpcCodec` 写按行的 Transport，不直接用 `StdioTransport`。
4. **Transport 关闭后，SDK 的 `Protocol` 不结束挂起的请求。** `Protocol` 只在 `close()` 时取消挂起的请求，而 Transport 的关闭只会结束它的读循环。处理：`BinderAcpTransport.bindTo(protocol, transport)` 在 `onClose` 里调 `protocol.close()`。之后挂起的请求以 `CancellationException("Protocol closed")` 结束，调用方要用通道的 `closeCause`（`peer_died` / `remote` / `violation` / …）区分对端死亡和自己取消。
5. **Binder 缓冲不足时，Java 层报的是 `DeadObjectException`。** 对端其实还活着。所以不能按异常类型判断死亡，要看 `isBinderAlive` 或死亡通知。
6. **窗口管不到接收方 SDK 内部的队列。** SDK 的 `asMessageChannel`、`ClientSessionHolder`、prompt 的更新通道都是无界 Channel；ack 在消息交给 SDK 时就发出。所以接收方 SDK 处理不过来时，积压留在 SDK 里，这是打满时延迟上升的主要原因。实际速率（每秒几百条以内）下不会出现。建议 W4 的更新映射把 Pi 的增量按 16–50 ms 合并后再发，降低条数。
7. **Agent 端所有请求和通知在一个单线程调度器上处理**（`Dispatchers.Default.limitedParallelism(1)`）。生产者如果在这个调度器上紧循环不挂起，同一连接上的 `session/cancel` 要等它让出才处理。假 Agent 用 `yield()` / `awaitWritable` / `delay` 避开；W4 的 AgentSide 不要在 SDK 的处理协程里做重活。
8. **客户端既不 close 也不释放、进程又一直活着时，`:agent` 那边的连接不会结束。** 对端持有本端接收端的引用，本端进程不死，死亡通知就不会来（按 Binder 的引用语义推断，没有单独测）。处理：`BinderChannel` 在外层作用域取消时主动通知对端关闭（“不调 close 直接 dispose”用例验证了这条路径）。W24 的 `AgentOs.kt` 要在 unbind 时关闭通道；`:agent` 侧的空闲超时由 W25 决定。

## 对 AgentOS 的影响

### 1. 一个 Transport，两端共用

已发布的 0.30.x 中，`Transport` 接口的主要方法是：

```kotlin
fun start()
fun send(message: JsonRpcMessage)      // 不挂起
fun onMessage(handler: (JsonRpcMessage) -> Unit)
fun onError(handler: (Throwable) -> Unit)
fun onClose(handler: () -> Unit)
```

参考：[0.30.0 Transport API](https://github.com/agentclientprotocol/kotlin-sdk/blob/v0.30.0/acp/src/commonMain/kotlin/com/agentclientprotocol/transport/Transport.kt)

`BinderAcpTransport` 基于 `binder-channel-v1` 的 `IChannel` 实现这个接口，客户端（`acp-android`、AgentOS 自带界面）和 Agent 端（`:agent` 运行时）用同一个类。第二部分验证后的做法：

- 入站：通道里的字符串在后台线程解码成 `JsonRpcMessage` → `onMessage`，然后回 ack；解码失败的消息跳过并计数（与 `StdioTransport` 一致）。
- 出站：`send` 只做 JSON 编码（按具体类型）和入队；Binder 调用在通道的写协程里，不在主线程；超长消息按 binder-channel-v1 第 7 节处理。
- 不要对 SDK 触发 `onError`：SDK 的 `asMessageChannel` 收到 error 会关掉消息通道。
- 关闭：通道因任何原因关闭都触发 `onClose`；接线时用 `bindTo` 把 `Protocol` 一起关掉。
- 给生产者一个 `awaitWritable`，因为 `send` 不能挂起。

### 2. `StdioTransport` 只用于电脑上的测试

SDK 内置的 `StdioTransport` 面向按行的输入输出。Android App 之间用 Binder Transport。电脑端网关（抽象 socket 上按行的 JSON）在第二部分里用 `StdioTransport` 验证过能通，但它输出的消息带 `"type"` 字段（问题 3），W9 要换成基于 `JsonRpcCodec` 的按行 Transport。

### 3. Ktor 模块可以用，但要选对引擎

如果将来使用 `acp-ktor-client`：

```kotlin
implementation("com.agentclientprotocol:acp-ktor-client:0.30.1")
implementation("io.ktor:ktor-client-okhttp:3.1.3")
```

ACP 的 Ktor helper 使用 WebSocket，而 Ktor 的 Android engine 不支持 WebSocket，Android 上应选 OkHttp 或 CIO。[Ktor 引擎说明](https://ktor.io/docs/client-engines.html)

AgentOS 的 ACP 走 Binder，不引入 `acp-ktor-client`。

## 需要锁定的风险

当前 `master` 分支的 Transport API 已经改成 `TransportFrame` / `onFrame`，而已发布的 0.30.x 仍是 `JsonRpcMessage` / `onMessage`。[当前 master API](https://github.com/agentclientprotocol/kotlin-sdk/blob/master/acp/src/commonMain/kotlin/com/agentclientprotocol/transport/Transport.kt)

**因此固定 Maven 版本 0.30.1，不能混用最新源码和旧版依赖。** 目前已有 0.31.0、0.32.0，升级 SDK 要单独评估：改 `BinderAcpTransport`，重新检查问题 2–4、6、7 是否还在，并在 API 35 / 36 / 37 的真机上重跑第二部分的用例。

如果 S5 为了 MCP Kotlin SDK 需要提高整个工程的 Kotlin 版本，第一部分要用新的工具链重跑一次，第二部分至少重跑 debug / release 的全矩阵。
