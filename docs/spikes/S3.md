# S3：ACP over Binder（官方 Kotlin SDK）

- **状态**：第一部分（编译与打包）已完成；第二部分（真机上的 Binder 往返）待做。
- **日期**：2026-09-28
- **对象**：官方 [`agentclientprotocol/kotlin-sdk`](https://github.com/agentclientprotocol/kotlin-sdk)，Maven 坐标 `com.agentclientprotocol:acp`
- **解锁**：W5（Binder 通道）

## 结论

**可以在 Android 15 / 16 上使用。** 准确地说：它是一个 JVM SDK，已验证能作为 Android 依赖接入；官方没有声明 Android target。

AgentOS 按计划推进：客户端和 Agent 端都用官方 SDK，Android 上的传输是自定义的 Binder Transport。

## 已确认的事实

- Android 15 对应 API 35，Android 16 对应 API 36。[Android API level 表](https://developer.android.com/guide/topics/manifest/uses-sdk-element)
- SDK 的 JVM 目标是 **Java 8 bytecode**，构建工具链要求 JDK 21。源码没有声明 `androidTarget()`，只有 JVM、JS、Wasm、iOS 等 target。[构建配置 v0.30.0](https://github.com/agentclientprotocol/kotlin-sdk/blob/v0.30.0/buildSrc/src/main/kotlin/acp.multiplatform.gradle.kts)
- Gradle 会把 `com.agentclientprotocol:acp:0.30.1` 自动解析到 JVM 变体 `acp-jvm`。[Maven Central 目录](https://repo1.maven.org/maven2/com/agentclientprotocol/acp/0.30.1/)
- Android 的 D8 / R8 支持 Java 8 bytecode 和相关 desugaring，因此这个结果符合 Android 的运行方式。[Java 8 支持说明](https://developer.android.com/studio/write/java8-support)

## 对 AgentOS 的影响

### 1. 一个 Transport，两端共用

已发布的 0.30.x 中，`Transport` 接口大致是：

```kotlin
send(message: JsonRpcMessage)
onMessage(handler: (JsonRpcMessage) -> Unit)
```

参考：[0.30.0 Transport API](https://github.com/agentclientprotocol/kotlin-sdk/blob/v0.30.0/acp/src/commonMain/kotlin/com/agentclientprotocol/transport/Transport.kt)

`BinderAcpTransport` 基于 `binder-channel-v1` 的 `IChannel` 实现这个接口，客户端（`acp-android`、AgentOS 自带界面）和 Agent 端（`:agent` 运行时）用的是同一个类。它需要负责：

- Binder 入站的字符串 → `JsonRpcMessage` → `onMessage`；
- `send(JsonRpcMessage)` → JSON 编码 → `IChannel.send(String)`；
- start、close、error 和背压；
- 不在主线程阻塞；
- 对端进程死亡时，经 `linkToDeath` 正确关闭协程和通道。

### 2. `StdioTransport` 只用于电脑上的测试

SDK 内置的 `StdioTransport` 面向 `System.in` / `System.out` 和命令行进程。Android App 之间的通信用 Binder Transport；`StdioTransport` 只用于在电脑上启动运行时、跑官方客户端的一致性测试。电脑端网关（抽象 socket 上按行分隔的 JSON）在第二部分里一并验证。

### 3. Ktor 模块可以用，但要选对引擎

如果将来使用 `acp-ktor-client`：

```kotlin
implementation("com.agentclientprotocol:acp-ktor-client:0.30.1")
implementation("io.ktor:ktor-client-okhttp:3.1.3")
```

ACP 的 Ktor helper 使用 WebSocket，而 Ktor 的 Android engine 不支持 WebSocket，Android 上应选 OkHttp 或 CIO。[Ktor 引擎说明](https://ktor.io/docs/client-engines.html)

AgentOS 的 ACP 走 Binder，不引入 `acp-ktor-client`。

## 需要锁定的风险

当前 `master` 分支的 Transport API 已经改成 `TransportFrame` / `onFrame`，而已发布的 0.30.x 仍是 `JsonRpcMessage` / `onMessage`。[当前 master API](https://github.com/agentclientprotocol/kotlin-sdk/blob/master/acp/src/commonMain/kotlin/com/agentclientprotocol/transport/Transport.kt)

**因此固定 Maven 版本 0.30.1，不能混用最新源码和旧版依赖。** 升级 SDK 要单独评估：改 `BinderAcpTransport`，并在 API 35 / 36 / 37 的真机上重跑第二部分的用例。

如果 S5 为了 MCP Kotlin SDK 需要提高整个工程的 Kotlin 版本，第一部分要用新的工具链重跑一次。

## 第二部分：真机验证（待做）

**做法**：做两个测试 App，结构与正式版一致。
- 客户端：SDK 的 Client + `BinderAcpTransport`；
- 服务端：SDK 的 Agent 端放在独立进程里（模拟 `:agent`），导出 `IAcpService`，同样用 `BinderAcpTransport`；
- 通道按 `binder-channel-v1` 草案实现：双方各实现一个 `IChannel`，`open` 时交换。

在 API 35、36、37 的真机上各跑一遍：

```text
initialize → session/new → session/prompt（流式输出）→ cancel → close / 重新 bind
```

debug 构建和 R8 release 构建各跑一次；过程中分别杀掉一次客户端进程和服务端进程；在流式输出的高峰下观察 Binder 异步缓冲。

最后让服务端开一个抽象 socket，Transport 按行收发 JSON，经 `adb forward` 用官方 TypeScript 客户端完成一轮对话。

**通过标准**：
- 流式输出不阻塞主线程，没有明显的延迟堆积；
- cancel 之后，这一轮返回 `stopReason: cancelled`；
- close 之后重新 bind，能正常继续；
- 任何一端进程死亡，另一端通过 `linkToDeath` 感知，并关闭对应的协程和通道，没有泄漏；
- R8 release 构建的行为和 debug 一致；
- 确定单条消息的上限（初定 128 KiB）和发送端背压参数，写进 `binder-channel-v1.md`；
- 电脑端经 `adb forward` 能完成对话。

**不通过时**：
1. 先修 `BinderAcpTransport`；
2. 如果是 SDK 在设备上的运行时问题，改为只用 SDK 的数据类型，自己写 JSON-RPC 层；
3. 官方 Java SDK 作为最后的备选。
