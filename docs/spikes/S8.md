## 结论

**a. 官方 SDK 能在 QuickJS 里跑通，不需要退路。** `pi-ai` 的 `anthropic-messages`、`openai-completions` 两个协议族连同两个官方 SDK，在 QuickJS 里完成了流式对话、工具调用、中途 `abort`、错误不重试、用保存的 messages 重建、多会话并发，两个协议族结果一致。条件只有三条：

1. 补一组 Web API polyfill（`spikes/S8/bundle/src/polyfills.js`）：真实定时器、流式 UTF-8 `TextDecoder`、`AbortController` / `EventTarget`、`Headers`、`Response`、`ReadableStream`、`URL` / `URLSearchParams`、`Blob` / `File` / `FormData`（SDK 在请求路径上用 `instanceof FormData` 判断）、`crypto.randomUUID`、`btoa` / `atob`。定时器和 `fetch` 只是宿主原语的薄封装，I/O 全在 Kotlin。
2. 三个文件换成空实现（`src/node-stubs/`）：`@anthropic-ai/sdk/internal/node.mjs`、`@anthropic-ai/sdk/tools/agent-toolset/node.mjs`、`pi-ai` 的 `utils/provider-env.js`。其余没有任何 `node:*` 引用，`build.mjs` 发现意外的 `node:*` 会报错。
3. 调用 `pi-ai` 时传入宿主 `fetch`、占位 key `agentos-host-injected-key` 和 `maxRetries: 0`（`src/stream-fn.js`，这就是交给 Pi 的自定义 `streamFn`）。`pi-ai` 自己已把 SDK 的 `maxRetries` 设为 0，再用 `retryProviderRequest` 按我们传的 `maxRetries` 重试，所以传 0 即完全不重试。

退路（宿主层实现两个协议族）没有实现：主路径已通过，`stream-fn.js` 的分发点就是将来换退路的位置。

**b. 一个 QuickJS 运行时承载多个会话，由"常驻泵"驱动；不用每会话一个运行时。**

- quickjs-kt 把同一实例上的顶层 `evaluate()` 串行化（`rootEvaluationMutex`），而且一次求值要等它发起的所有异步绑定结束才返回。如果像原型那样"一轮 prompt 一次 evaluate"，另一个会话的 prompt、甚至同一会话的 `abort` 都要排队到这一轮结束。所以无论一个还是多个运行时，都需要泵：宿主只求值一次 `__pi_main()`，它挂在 `__host_next()` 上取命令，每条命令异步分发、不互相等待，结果和事件经 `__host_emit()` 回到 Kotlin。
- 内存差两个数量级：一个运行时加载 bundle 后 native 堆约 +5 MB（4 个运行时 +20 MB，PSS +20 MB）；同一运行时里每多一个会话约 +18 KB（一轮短对话后，随 messages 增长）。
- 并发不受影响：同一运行时 10 个会话同时各跑一轮，墙钟 266 ms，单会话一轮 256 ms。JS 只做协议转换，耗时在网络上。
- 风险：quickjs-kt 遇到跨过一次宿主往返仍未处理的 Promise rejection，会终止根求值，也就是整个泵（1.0.5 和 1.0.15 行为相同）。上游代码在所有用例（含 abort、4xx/5xx）里都没有产生这种 rejection，用例是人为注入的。处理方式按 F8 的运行时崩溃对待：泵退出后，后续请求约 1 ms 内失败（不会挂住）；正在进行的轮次标记为需要恢复、不自动重放；新建运行时并用 Store 里的 messages 重建会话，实测约 70 ms（含加载 bundle）。如果以后需要隔离，可以把会话分片到少数几个运行时，不需要一会话一个。

**c. 电脑上跑 bundle 有两种方式，跑的是同一个 `pi-agent.js`：**

- **JVM 上用同一个绑定 `quickjs-kt`**（Gradle 解析到 `quickjs-kt-jvm`，jar 自带 macOS arm64 / x64、Linux arm64 / x64、Windows x64 的原生库）。`JsEngine` 的电脑实现就用它，`core/runtime` 的 JUnit 和 `tests/acp-conformance/` 走这条，引擎与手机上完全相同。本次只在 macOS arm64 上验证；CI 的 Linux x64 待 W1 的 CI 验证。
- **Node 的裸 `vm` 上下文**（只有 ECMAScript 内置对象，没有 fetch、定时器、TextDecoder，与 QuickJS 的环境等价），宿主原语用 Node 实现（`spikes/S8/bundle/test/vm-host.mjs`）。用于 `core/pi-runtime/test` 的快速契约测试，不需要 JVM。

**d. quickjs-kt 用 1.0.15，但它要求 Kotlin 编译器 ≥ 2.3，与计划锁定的 Kotlin 2.2.20 冲突，需要整合人决定升级。**

| 组合 | 结果 |
|---|---|
| Kotlin 2.2.20 + quickjs-kt 1.0.15 | 编译失败：1.0.15 用 Kotlin 2.4.10 构建（元数据 2.4.0），并把 `kotlin-stdlib` 带到 2.4.10；2.2 编译器最多读 2.3 |
| Kotlin 2.2.20 + quickjs-kt 1.0.5（最后一个用 Kotlin 2.3 构建的版本） | 能编译，其余用例通过，但带中文和 emoji 的那一轮挂住：请求没有发出，JS 和宿主都在等待。根因没有单独定位；按变更记录，对应 1.0.15 的"JNI 字符串转换的 Unicode / emoji 修复"和 1.0.14 的"绑定异常传播修复"。另外缺 1.0.7 的原生生命周期与加锁修复。**不可用** |

## 真实端点（2026-09-29 整合时）

key 是用户提供的 MiniMax 国内平台 key，存在仓库外的 `agentos-workspace/.secrets/minimax.env`（权限 600，不进任何仓库）。用户指定 Anthropic 推理接口 `https://api.minimax.cn/anthropic/v1/messages`。`pi-ai` 目录里的 `minimax-cn` 预设用的是 `https://api.minimaxi.com/anthropic`，所以两个都测：新增可选环境变量 `MINIMAX_ANTHROPIC_BASE_URL`（Android 上是 intent extra `minimaxBaseUrl`），在同一个 `minimax-cn` 预设上只替换 baseUrl，模型参数不变，作为目标 `minimax-cn@custom-base`。

## 给 W3 / W6 的设计要点

> W3 已按这里实现，协议 v1 的正式说明在 [core/pi-runtime/README.md](../../core/pi-runtime/README.md)。下面保留 S8 的结论，并标出实现时修正的三处。

**宿主原语**（JS 看到的全部外部能力，Android 与电脑实现同一组）：

| 原语 | 同步 / 异步 | 作用 |
|---|---|---|
| `__host_emit(json)` | 同步 | 事件、命令回复、日志 |
| `__host_next()` | 异步 | 取下一条命令；返回 null 表示关闭 |
| `__host_timer(id, ms)` / `__host_timer_cancel(id)` | 异步 / 同步 | 真实定时器（协程 `delay`） |
| `__host_fetch(reqId, requestJson)` | 异步 | 发请求，返回状态码和响应头；请求带发起会话的 `sid` |
| `__host_fetch_read(reqId)` | 异步 | 读下一段响应体（`Uint8Array`），EOF 返回 null |
| `__host_fetch_abort(reqId)` | 同步 | 取消 OkHttp 调用、关闭连接 |
| `__host_call(method, json)` | 异步 | 工具执行、`beforeToolCall`、`afterToolCall` 回到 Kotlin |

**命令**：`create`（sid、model、systemPrompt、tools、可选 messages）、`prompt`（在 `agent_end` 之后回复 stopReason 和本轮新增的 messages）、`abort`、`setTools`、`setModel`、`history`、`dispose`、`stats`。事件在 JS 侧压缩：`message_update` 只带 delta，不带整条 partial message，避免每个 token 都序列化整段消息。

**线程**：每个运行时一个单线程调度器，同时作为 quickjs-kt 的 `jobDispatcher`；QuickJS 实例也在这个线程上创建、定义绑定；阻塞读放到 `Dispatchers.IO`。`__host_emit` 在 JS 线程上同步回调，宿主要尽快转交（例如投进 Channel），不能在里面做 I/O。

**HostFetch**：只替换值等于占位 key 的 `x-api-key` / `Authorization: Bearer` 头，且只对配置了凭据的 endpoint 替换（按 scheme、host、port、路径段匹配），找不到凭据就不发请求；丢弃 JS 传来的 `accept-encoding`、`content-length`、`host`、`connection` 等（否则 OkHttp 不再自动解压）；不跟随重定向（重定向可能把 key 头带到别的主机）；`retryOnConnectionFailure(false)`；`readTimeout` 要足够长（SSE 在推理时可能长时间没有字节），deadline 由宿主层管。JS 侧在 abort 时立即让响应流报错，不等宿主读任务返回。实现时修正两处：
- **取消必须 `call.cancel()`**：只关闭 response body 时，OkHttp 会先尝试把没读完的流读掉（最多 100 ms），读不完只把连接标记为不再复用，socket 并不立即关闭，服务端继续生成。S8 的 Kotlin 宿主用的是 `call.cancel()`，所以当时没暴露；W3 契约测试里服务端检查到连接被关闭。
- **`retryOnConnectionFailure(false)` 也关掉了同一次请求内换 IP 地址**（例如 IPv6 不通时改走 IPv4）。换地址要靠宿主重试策略的下一次尝试（OkHttp 的路由表会跳过失败的地址），所以生产配置的 `RetryPolicy.maxAttempts` 至少为 2。宿主重试只发生在响应头交给 JS 之前，不会重复已流出的内容。

**`JsEngine` 只做最小绑定，消息协议放在 `core/runtime` 的 `PiRuntime` 里**（修正 S8 的说法）：S8 建议把 `JsEngine` 设计成 `start / send / 事件 / close` 的消息接口。实现时把它拆成两层：`JsEngine` 只负责定义宿主函数、求值、编译字节码、内存统计和关闭；泵、宿主原语、协议版本检查、字节码缓存和"泵已退出"的通知都在平台无关的 `PiRuntime` 里。Android（W6 的 `QuickJsEngine`）和电脑（testFixtures 的 `QuickJsJvmEngine`）因此只各有几十行，行为由同一份代码和同一套测试保证。上层仍然只按消息使用（`PiRuntime.request` 和类型化的 `createSession / prompt / abort …`），不要每个操作一次 evaluate。原型用 `interruptEvaluation` 做取消，会直接打断求值，Pi 走不到 `aborted` 收尾，不要用。

**quickjs-kt 把 `ByteArray` 转成 `Int8Array`**，`UByteArray` 才转成 `Uint8Array`。引擎实现返回响应体时要用 `bytes.asUByteArray()`（零拷贝），否则 JS 侧要再拷贝一次。

**0.86.1 与原型的 0.85.1 的差异**：system prompt 作为一条 `role: "system"` 的消息存在 `messages` 开头（`history` 里包含它，重建时原样传回即可，不会重复）；`Agent` 需要显式的 `streamFn`；`pi-ai` 各协议族改为懒加载模块，按文件路径直接引入即可。

**bundle 里没有 `eval` 和 `Function` 构造器**（`build.mjs` 发现即失败），以后可以考虑在 QuickJS 里关闭 eval 作为加固（原则 8）。

**MiniMax-M2.7 的 thinking**（W3 真实端点冒烟测试，2026-09-29）：`minimax-cn` 预设（`reasoning: true`，思考级别 off 时 `pi-ai` 发 `thinking: {type: "disabled"}`）、自定义端点模板默认值（`reasoning: false`，不发 `thinking` 参数）和自定义端点 `reasoning: true` 三种配置下，M2.7 都会输出 thinking 块；对话、跨轮回忆、工具调用（thinking + tool_use，再带 thinking 回传工具结果）、abort 全部通过。`pi-ai` 对 thinking 块的解析和回传不看 `reasoning`，所以自定义端点模板默认 `reasoning: false` 可以正确处理 M2.7；`reasoning` 只影响请求参数和设置页的展示。

## `model-catalog.json` 格式（给 D：设置页的厂商预设）

正式说明（schemaVersion 1）见 [core/pi-runtime/README.md](../../core/pi-runtime/README.md#model-catalogjsonschemaversion-1)，Kotlin 解析见 `org.agentos.runtime.pi.ModelCatalog`。要点：

```jsonc
{
  "schemaVersion": 1,
  "generatedFrom": { "@earendil-works/pi-ai": "0.86.1" },
  "apis": ["anthropic-messages", "openai-completions"],
  "customTemplates": {            // 自定义兼容端点：设置页补上 id、name、baseUrl
    "anthropic-messages": { "api": "anthropic-messages", "provider": "custom", "reasoning": false, "input": ["text", "image"], "cost": { ... }, "contextWindow": 128000, "maxTokens": 8192 },
    "openai-completions": { ... }
  },
  "providers": [
    {
      "id": "minimax",
      "name": "MiniMax",
      "apis": ["anthropic-messages"],
      "baseUrls": ["https://api.minimax.io/anthropic"],
      "auth": { "type": "api-key", "label": "MiniMax API key" },
      "models": [
        // pi-ai 的 Model 对象，原样作为 create 命令的 model 传给 JS
        { "id": "MiniMax-M2.7", "name": "MiniMax-M2.7", "api": "anthropic-messages", "provider": "minimax",
          "baseUrl": "https://api.minimax.io/anthropic", "reasoning": true, "input": ["text"],
          "cost": { "input": 0.3, "output": 1.2, "cacheRead": 0.06, "cacheWrite": 0.375 },
          "contextWindow": 204800, "maxTokens": 131072 }
      ]
    },
    { "id": "minimax-cn", "baseUrls": ["https://api.minimaxi.com/anthropic"], ... }
  ]
}
```

- 设置页展示 `providers[].name`、`models[].name` 和 `contextWindow`、`maxTokens`、`reasoning`、`input`；用户只填 key。
- 模型对象里可能还有 `compat`、`thinkingLevelMap`、`headers`、`promptCache` 等字段，界面不用理解，原样保存、原样传给运行时。
- key 按 `baseUrls` 与厂商对应，由宿主层注入，不写进这个文件或模型对象。
- 导出时跳过了 `cloudflare-ai-gateway`、`cloudflare-workers-ai`（baseUrl 需要账号 ID）和 `github-copilot`（订阅账号的登录 token，首版不做订阅登录，F9）。`kimi-coding`、`openrouter`、`anthropic` 等同时支持 OAuth 的厂商，目录里只按 API key 使用。
- **OpenAI 官方预设不在目录里**：`pi-ai` 0.86.1 的 `openai` 厂商全部走 `openai-responses` 协议，不在打包的两个协议族内。用户可以用"自定义兼容端点 + OpenAI Chat Completions"接 `api.openai.com`。

## 风险与待办

1. **真机**：API 35 / 36 / 37 真机上重跑 `tools/run-android.sh release contract,measure` 和 `tools/cold-start-android.sh`，补冷启动和内存数值。需要整合人分配 `ANDROID_SERIAL`。
2. **真实端点**：MiniMax 国内已在电脑和模拟器上通过（见“真实端点”）。还差：真机上跑 `tools/run-android.sh release real`；国际预设需要国际平台的 key；OpenAI 兼容端点设置 `OPENAI_COMPAT_*` 后跑。本机运行前 `set -a; . agentos-workspace/.secrets/minimax.env; set +a`。
3. **Kotlin 版本**：已按结论 d 升到 2.3.20（整合人决定）；最终版本与 S5 一起定，升到 Kotlin 2.4 时一并评估 AGP（R8 元数据警告）。quickjs-kt 的传递依赖会把 `kotlin-stdlib` 拉到 2.4.10、`kotlinx-coroutines-core` 拉到 1.11.0，见 W3 报告。
4. **未处理的 rejection 会终止泵**：W3 已按运行时崩溃处理（`PiRuntime` 进入 `Stopped`，后续请求立即失败，由上层重建），可以向 quickjs-kt 上游提议"未处理 rejection 只报告、不终止根求值"的选项。
5. **Linux x64 上的 quickjs-kt-jvm**：jar 里有原生库，但只在 macOS arm64 上验证过，W1 的 CI 需要跑一次。
6. **ABI**：测试 App 带了 4 个 ABI 的 `libquickjs.so`（约 3.3 MB），正式 App 可以只保留 arm64-v8a（和模拟器需要的 x86_64）。
